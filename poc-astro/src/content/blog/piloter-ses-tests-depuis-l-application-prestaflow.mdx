## Préambule

Les deux premiers articles de la série nous ont donné les deux modes d'usage naturels de PrestaFlow :

* [**Article 1**](/blog/ecrire-son-premier-scenario-prestaflow/) — la librairie PHP : on écrit ses scénarios et on les lance à la main avec `composer prestaflow -- run ./tests/prestaflow`.
* [**Article 2**](/blog/automatiser-ses-scenarios-prestaflow-en-ci/) — la GitHub Action : on délègue cette exécution à GitHub Actions à chaque commit, avec matrice multi-versions PS et remontées sur la plateforme.

Il reste un troisième mode d'usage, plus interactif : **piloter ses scénarios depuis une interface graphique**, en boucle courte, pendant le développement. C'est ce que fait l'application desktop PrestaFlow.

Ce n'est pas un remplaçant de la CLI ni du CI — c'est un complément, pensé pour les moments où on écrit un scénario, on l'ajuste, on relance, on regarde une capture, on ajuste encore. Là où repasser par le terminal casse le flux.

<Info title="Preview — l'application est en préparation">
L'application desktop décrite dans cet article est encore en construction et n'est pas disponible en téléchargement. Ce qui suit décrit **à quoi elle ressemblera** au moment de sa sortie ; les captures d'écran sont des **mockups** issus des designs en cours. Ce qui est en revanche accessible dès aujourd'hui, c'est la **beta privée de la plateforme prestaflow.io** — vous pouvez déjà y brancher vos runs CLI et CI (voir la section suivante).
</Info>

## L'app en un paragraphe

L'application PrestaFlow est un **desktop app** construit avec [NativePHP](https://nativephp.com) et Laravel. Elle tourne localement sur votre machine, lit vos projets PrestaFlow (le module et son dossier `tests/prestaflow/`), exécute les suites via un **runner interne** (elle instancie les classes `TestsSuite` directement en PHP, pas de shell-out vers la CLI) et affiche les résultats dans une UI dédiée. Un **sync cloud optionnel** pousse les runs vers [prestaflow.io](https://prestaflow.io) pour l'historique et les tableaux de bord.

## Beta privée — plateforme prestaflow.io

En attendant l'app, la partie **plateforme** (API + dashboards sur `prestaflow.io`) est déjà en **beta privée sur invitation**. C'est elle qui reçoit les runs remontés par la GitHub Action (voir [l'article 2](/blog/automatiser-ses-scenarios-prestaflow-en-ci/)) et, plus tard, par l'app desktop.

Pour demander l'accès, inscrivez-vous sur la [waitlist](https://prestaflow.io/waitlist) de prestaflow\.io. Quand votre tour arrive, vous recevez :

* un accès à votre espace sur [prestaflow.io](https://prestaflow.io),
* la **Product Key** `pk_...` à passer à l'Action GitHub pour envoyer vos runs CI vers vos dashboards,
* plus tard, un lien de téléchargement de l'app desktop dès qu'elle sera prête pour la beta.

La suite de l'article décrit le flux **end-to-end** tel qu'il se présentera avec l'app — utile pour se projeter et comprendre où viendront se brancher les pièces qui manquent encore.

## Premier lancement — connecter son compte

Au premier démarrage, l'app demande de se connecter avec les identifiants prestaflow\.io. Deux méthodes disponibles :

* **Sign-in GitHub** — flux OAuth classique, redirection navigateur.
* **Email + mot de passe** — l'espace créé lors de la demande d'accès.

Une fois authentifié, un fichier `.deviceToken` est créé dans le dossier user-data de NativePHP (`~/Library/Application Support/PrestaFlow/` sur Mac). C'est ce jeton qui sera utilisé pour toutes les interactions futures avec la plateforme.

## Ajouter psflowdemo comme projet local

L'app fonctionne autour de la notion de **projet local** : un dossier sur votre disque qui contient un module PrestaShop équipé de PrestaFlow (typiquement le résultat des articles 1 et 2).

Depuis l'écran principal, **Add project** ouvre un sélecteur de dossier. Pointez sur la racine du module `psflowdemo` — celle qui contient `composer.json`, `.env` et `tests/prestaflow/`.

L'app scanne l'arborescence, détecte :

* les **suites** dans `tests/prestaflow/Suites/` (dans notre cas, celles de l'article 1 : `Checkout`, `DisplayHome`, `UpdateTitle` ; le dépôt psflowdemo en ajoute deux, `Smoke` et `Regression/NoXssInBlockTitle`),
* les **Pages custom** dans `tests/prestaflow/Pages/` (notre `Modules\Psflowdemo\Home`).

Les paramètres de la boutique (URLs BO/FO, identifiants, locale, version PS), eux, ne sont pas lus dans le `.env` : ils se règlent dans la carte **Shop configuration** des réglages du projet, et chaque suite peut les surcharger. Reportez-y les valeurs de votre `.env`.

Le projet apparaît dans la sidebar. La vue projet liste vos suites, chacune avec son statut du dernier run (jamais joué / passé / échoué).

<img src="/posts/2026-07-31-piloter-ses-tests-depuis-l-application-prestaflow/screen-project.svg" alt="Vue projet psflowdemo avec les trois suites détectées" />

## Exécuter une suite depuis l'UI

Un clic sur une suite ouvre sa vue de détail. Un bouton **Run** en tête déclenche l'exécution.

Sous le capot, l'app dispatche un job Laravel (`ExecuteSuite`) qui instancie la classe `TestsSuite` de votre suite avec les réglages de la boutique (URLs, identifiants, locale) enregistrés dans l'app, puis appelle `->run(cli: false)`. Pas de shell-out, pas de sous-processus PHP : l'app **est** l'exécuteur.

Concrètement, ça veut dire :

* l'app pilote Chrome (via [chrome-php/chrome](https://github.com/chrome-php/chrome), la même dépendance que la CLI),
* les étapes s'exécutent une à une,
* l'UI affiche la progression au fil de l'eau : étape en cours, étapes passées avec leur durée, échec éventuel.

<img src="/posts/2026-07-31-piloter-ses-tests-depuis-l-application-prestaflow/screen-run-progress.svg" alt="Exécution en cours d'une suite avec progression étape par étape" />

En fin de run, la vue résultat s'affiche automatiquement.

## Lire un résultat

La vue résultat est le point central de l'app. Elle affiche, pour un run donné :

* **La liste des étapes** avec leur statut (vert / rouge / gris pour skipped ou todo) et leur durée individuelle.
* **La capture de l'échec**, cliquable pour l'agrandir. Comme avec la CLI, il n'y en a pas pour les étapes qui passent : la librairie ne prend une capture pleine page qu'au moment où une assertion échoue. Elle montre l'état de la page à cet instant, souvent suffisant pour comprendre.
* **Le stack trace** en cas d'exception, avec pointeur sur le fichier de la Page ou du Scenario.
* **Les stats du run** : passes / failures / skips / durée totale.

<img src="/posts/2026-07-31-piloter-ses-tests-depuis-l-application-prestaflow/screen-result-detail.svg" alt="Vue détaillée d'un run avec captures et statuts" />

L'app conserve un **historique local** de tous les runs joués depuis qu'elle est installée. On peut y revenir à tout moment via la sidebar : rouvrir un run d'hier, regarder sa capture, puis rebasculer sur le run d'aujourd'hui pour voir ce qui a changé quand quelque chose se met à casser.

<Info title="Boucle courte typique : on écrit un it, on Run depuis l'app, on voit la capture, on ajuste le sélecteur dans la Page, on Run à nouveau. Pas de terminal, pas de recompilation, pas de perte de contexte.">

</Info>

## Sync cloud — lier le projet à prestaflow\.io

Tant qu'on reste local, l'app est autonome. Mais si vous utilisez déjà la plateforme (parce que vous avez suivi [l'article 2](/blog/automatiser-ses-scenarios-prestaflow-en-ci/) et branché l'Action GitHub), il devient intéressant de faire remonter vos runs locaux au même endroit — pour avoir tout l'historique (local + CI) sur le même dashboard.

Une seule étape de config, une fois par projet.

### Le sync suit votre connexion

Il n'y a pas d'interrupteur à activer : **Settings → Cloud** affiche le compte connecté et rappelle que les runs sont synchronisés automatiquement tant que vous êtes connecté. Encore faut-il dire à quel projet prestaflow\.io rattacher le projet local : tant qu'il n'est lié à aucun, ses runs restent sur votre machine.

### Lier le projet local au projet cloud

Depuis la page **Settings** du projet `psflowdemo` (sidebar → projet → Settings), cliquez sur **Link to cloud project** dans la carte **Cloud link**. Une modale affiche la liste de vos projets prestaflow\.io — c'est la même liste que celle utilisée pour l'Action GitHub, avec les mêmes Product Keys `pk_...`.

Sélectionnez le projet correspondant. La Product Key est stockée localement, dans la config du projet.

<img src="/posts/2026-07-31-piloter-ses-tests-depuis-l-application-prestaflow/screen-cloud-link.svg" alt="Liaison du projet local à un projet cloud" />

## Pousser un run vers la plateforme

Une fois le projet lié, chaque run terminé part automatiquement vers l'API `api.prestaflow.io` (résultats, captures, régressions visuelles s'il y en a). Un run qui n'a pas encore été envoyé expose un bouton **Sync now** pour le pousser à la main.

La vue de run affiche l'état de l'envoi : **Synced to prestaflow\.io**, avec un lien **Open on prestaflow\.io**, en cas de succès ; **Sync failed**, avec l'erreur et un bouton **Retry**, sinon.

<img src="/posts/2026-07-31-piloter-ses-tests-depuis-l-application-prestaflow/screen-sync.svg" alt="Bouton de sync sur la vue résultat, avant et après" />

Côté plateforme, le run apparaît dans l'historique du projet, aligné avec les runs remontés par l'Action GitHub. C'est là que la trilogie boucle : que vous testiez à la main (app), en local (CLI) ou en CI (Action), tout converge vers la même timeline. La sidebar de l'app signale les échecs de sync par un badge **Sync failed** accompagné de leur nombre, pour éviter que des runs restent oubliés en local.

## Où l'app se positionne par rapport au reste

Les trois modes d'usage ne se remplacent pas — ils couvrent trois moments différents du cycle de développement d'un module :

* **CLI** : le mode reproductible. Ce qui se joue en CI se joue à l'identique en local. Pas de dépendance graphique, scriptable, versionnable.
* **CI (Action GitHub)** : le mode automatique. Chaque commit est testé sur chaque version PS supportée, sans intervention.
* **App** : le mode interactif. Boucle courte pendant l'écriture d'un scénario, historique local, sync vers la plateforme quand on veut consolider.

Un dev qui publie des modules open-source va typiquement utiliser les trois : app pour écrire et itérer, CI pour le filet de sécurité, CLI en dépannage ponctuel ou en environnement contraint.
